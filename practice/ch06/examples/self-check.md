# 自查反馈：不要越过已有证据

> 预设反馈，针对教学过程卡；不是实测结论。先自己分类，再来对照。

| 步骤 | 建议分类与状态 | 能支持什么、不能支持什么 |
| --- | --- | --- |
| T1 | 读取；两份返回成功 | 假设情境中拿到 A 与原稿；尚不能说读到 B |
| T2 | 读取请求已执行，但失败 | 错路径未找到文件；不能把失败写成未请求，也不能据此说所有步骤失败 |
| T3 | 有边界的重试；读取成功 | 正确路径的 B 返回；仍应保留 T2，不把重试范围扩大到整个电脑 |
| T4 | 生成候选；未保存 | 能看到拟修订文字；没有实际文件证据 |
| T5 | 额外建议；被拒绝、未执行 | 人没有授权发布，也没有发布尝试；不是“发布成功”或“发布失败” |
| T6 | 写入请求；先待批准，后获批准 | 批准限定本次新文件；批准不是执行结果，更不是长期全面授权 |
| T7 | 写入执行；返回成功 | 工具报告新文件已创建；内容和路径仍需实际核验 |
| T8 | 读回；取得文件内容 | 支持核对保存内容与候选是否一致；若只读到片段，要保留未读范围 |
| T9 | 人的产物与内容核验 | 在此情境中完成局部检查；没有获得真实读者反馈，也没有发布 |

“执行”是宽泛类别，读取文件本身也是工具执行。为了看清任务，本表把读取、生成、写入分别标出；不必为一个唯一术语答案争论，关键是说明对象、状态和证据。

## 一段合格的总结可以是什么样

“我阅读的是教学设计轨迹，不是自己的运行日志。情境中 T2 读错路径失败，T3 在确认已授权路径后取得材料；T4 的文字尚未保存，T5 的发布建议被拒，未执行。T6 批准只允许创建一个新候选，T7 报告创建成功，T8 读回，T9 由人核查内容。局部任务在假设情境中完成，但本课程没有据此证明 DSH 真实运行成功，也未验证读者效果。”

## 导览修订参考

原句“打开 DSH 网页，就能自动完成文件任务”混淆了入口、使用条件与实际结果。T4 的修订句可作为一种方案：B1 支持服务和模型准备，B2 支持工作区选择，B3 支持文件工具能力与检查实际任务的必要边界。标编号之后仍要打开材料核对。

有自己的导览时，可能原本已经写得准确，不必强行改错；可以保留原句，并补一条“本次确认无须修改”的依据。没有真实运行时，不在导览里新增“我已成功使用 DSH”之类声明。

## 三个容易混淆的地方

1. **没有审批弹窗，不代表没有权限边界。** 是否询问取决于实际策略和动作。观察不到配置时写“未显示”，不推出无权限限制。
2. **模型说明理由，不等于完整内部思维。** 任务轨迹只记录可见输入、请求、返回与产物；不编造看不见的计算过程。
3. **人工保存可以是可用替代，但必须换标签。** 普通聊天工具输出候选后由人保存，记“模型生成、我保存”，不能记“DSH 写入成功”。

完成阅读判断以后，可在接入条件落实时再做真实路径。两份记录分别保留，不能把示例日期、工具状态或成功结论复制成自己的经历。

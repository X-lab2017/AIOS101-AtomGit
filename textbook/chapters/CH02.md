# 开源项目的结构与运作：从项目全貌到材料与协作

> 状态：published
> 版本：0.5.0

**打开一个开源项目，怎样看懂它在做什么、怎样运作？**首页上的名称、图表或下载按钮只能给出初步印象。要继续学习，需要把目的、成果、材料以及建设这些成果的人联系起来。

本章用 OpenDipper 的公开材料演示项目阅读方法，再比较 DSH 软件工具、R1 模型及数据研究项目。它们提供不同成果，阅读时既有共同问题，也有各自的重点。你可以从本章完整材料中选择一个对象，制作一份有依据的项目画像，无需携带第一章的作品。

## 学习目标与阅读准备

学习本章后，应能够：

- 从目的、成果、材料与协作解释项目，区分项目、仓库与平台。
- 按问题选择 README、文件目录、研究说明、版本记录与贡献指南。
- 比较软件工具、模型和数据研究项目的材料特点，说明判断范围。
- 使用本章材料制作项目画像，解释材料选择及一个待解问题。

本章以第一章的模型、产品、项目和材料判断概念为基础，无需编程先修。正文提供中文材料卡、例题与反馈；在线阅读可使用 GitHub、Hugging Face 和 AtomGit。无需安装 DSH、下载模型或向社区提交内容。平台操作放在配套材料中，核心是建立能够迁移的阅读方法。

## 2.1 项目的目的与成果

### 2.1.1 从真实需要理解项目价值

看到一个项目时，可以先问：它为谁解决什么问题？一个模型帮助处理语言任务，一项工具帮助组织操作，一份数据产品帮助了解某类现象。名称和功能表需要放回具体使用情境，才容易理解其价值。

**项目**把目标、成果以及建设和改进成果的工作组织在一起。它可能交付软件、数据、模型、教材，也可能同时提供多种成果。公开仓库只是一个入口，其他知识可能分布在文档站、模型平台和讨论区。阅读这些入口，有助于把零散印象组织成完整认识。

以 OpenDipper 为例，它提供开源生态的观测与研究入口。仅从界面看，它像一个图表网站；继续追问“这些图表帮助谁了解什么”，就需要阅读来源、数据解释、设计与协作材料。本章用这个例子学习阅读方法，学生也可以把同一方法用于其他项目。

### 2.1.2 目的、成果、材料与协作的全貌

| 阅读问题 | 寻找的内容 | 与其他问题的联系 |
| --- | --- | --- |
| 目的：为谁解决什么问题？ | 目标读者、使用情境和需要 | 决定成果为什么值得建设 |
| 成果：提供了什么？ | 程序、模型、数据、文档或服务 | 说明使用者可以取得或使用什么 |
| 材料：成果怎样形成？ | 来源、代码、数据、方法与检查 | 帮助理解实现方式与依据 |
| 协作：怎样共同改进？ | 角色、反馈、贡献规则与维护 | 解释成果如何继续发展 |

![从目的、成果、材料与协作读懂一个项目](../assets/figures/ag-02-01-project-whole.svg)

图 AG-02-01 用 OpenDipper 展示四个问题的联系。这是项目阅读框架，箭头不表示软件的自动执行流程。先用共同问题建立全貌，再依据自己的问题选择材料。

**材料 A：OpenDipper 的目标与当前成果。**以下依据项目固定版本 README 整理[1]。

- **A1 · 用途。**项目服务于 AI 与开源生态探索，帮助使用者发现对象、组织来源、准备研究和交付报告。
- **A2 · 成果。**入口包括全球观测、AI 雷达、开源星系、智能体情报室与社区。模块共同支持发现、阅读、整理和研究等工作，不只提供模型下载。
- **A3 · 阅读路径。**README 提供一次从官方来源进入知识整理、再阅读和编辑报告的示例。该示例不需要 API 密钥。
- **A4 · 当前范围。**上述完整报告是编写好的示例，不是现场运行 DSH 生成的结果；该版本说明研究执行服务尚未接通。数据还有各自的观察时间与样本范围。

读材料 A 时，A1 说明目标，A2—A3 介绍使用者可以看到的功能与路径，A4 交代当前实现范围。四者缺一，项目介绍都容易失真：只列功能而忽略范围，会把计划或示例当成已经实现的能力；只记录限制而不理解目的，也无法判断项目为何值得研究。

**例 2-1　“能够展示报告”说明了什么？**一位读者看到完整报告，写下“OD 已接通 DSH，能自动完成全部研究”。这句话把界面上可见的成果与成果产生的过程合并了。根据 A3—A4，更合适的表述是：“该版本提供了完整的报告示例，支持阅读、编辑和导出；现场研究执行尚未接通。”下一步可以研究示例怎样组织引用，但不能把示例当作实际运行记录。

这一方法适用于其他项目：把“目标是什么”“当前能做什么”“还有什么条件”一起读。项目处于建设过程中并不妨碍学习；明确阶段，反而能帮助我们理解改进从何处发生。

### 2.1.3 项目、仓库与平台的关系

**仓库（Repository）**是组织项目文件及其修改历史的空间。常见仓库由 Git 这样的版本管理工具记录变化：哪些文件发生修改，修改形成了什么状态，以及后续怎样继续演进。初学时不必先操作命令，只要理解仓库既保存文件，也保存文件怎样变化的线索。

**项目与仓库并不是一一对应的关系。**一个项目可以同时维护程序仓库、文档仓库和数据仓库；一个仓库也可能包含多个工具。OpenDipper 的主仓库提供程序与说明，它所用的部分数据另有上游来源；DeepSeek-R1 的说明仓库与模型文件入口也分布在不同位置。读到一个仓库，不等于已经取得项目的全部材料。

常见地址用 `拥有者/仓库名` 标识对象。例如，`X-lab2017/open-dipper` 表示组织账号 X-lab2017 下的 open-dipper 仓库。完整标识比简称更适合查证：同名对象、社区衍生项目与原始发布项目可能来自不同账号。确认入口时，可交叉查看项目主页、README 与组织账号提供的链接，不能只选择搜索结果中名字最像的一项。

**平台**为许多项目提供承载与协作服务，不是某个具体项目本身。本课接触的三个平台有不同侧重，但功能存在交叉。

| 平台 | 本课主要用它做什么 | 阅读时应辨认什么 |
| --- | --- | --- |
| GitHub | 查看案例项目的仓库、修改记录与公开讨论。 | 账号、仓库、文件路径和对应版本。 |
| Hugging Face | 查看模型、数据集与应用空间的材料。 | 对象类型、发布者、说明卡、文件与适用条件。 |
| AtomGit | 保存作品、版本与协作记录。 | 自己的作品、来源记录、变化与协作约定。 |

去哪个平台，首先取决于要找哪份原始材料。把研究作品放到 AtomGit，并不要求把案例的所有文件搬过去。学习者可以整理自己的解释与来源，后续再按需要分享和共同修订。

## 2.2 项目材料的阅读与选择

### 2.2.1 从 README 建立阅读路径

**README** 的意思接近“请先读我”，通常是项目的入口说明。它可能介绍目的、主要功能、开始方式、相关文档和参与路径[5]。它既帮助人开始，也帮助人决定“下一步读哪里”，并不是一份必须逐行读懂的全部知识。

读 OD 的 README，可以先用一句话回答“谁需要它”；再查看“可以做什么”与范围说明；接着只追踪与自己问题有关的链接。例如，要判断图中一条连线意味着什么，应到关系说明；想为术语解释提供帮助，应读贡献指南。安装命令适合准备运行软件的人，暂时不运行时可以保留位置，不必让它阻断概念阅读。

这是**按问题阅读**：先提出一个需要回答的问题，再寻找能提供相应信息的材料。与从头抄到尾相比，它要求读者作出选择，也更容易发现哪里缺少依据。

### 2.2.2 程序、数据、文档与使用说明

第一次打开仓库，常见困难是文件很多，名字陌生。可以先辨认职责：哪些文件给人解释，哪些文件给程序执行，哪些提供输入，哪些用于检查结果。识别职责不等于掌握文件内容，却能帮助我们选择阅读顺序。

**材料 B：OpenDipper 的材料组织。**以下概述依据 README 的技术视图与文档导航[1]。它描述该版本公开说明的材料关系，不代表本章已经运行了程序。

- **B1 · 输入。**项目组织 OpenDigger 等来源的数据，以及官方发布、来源记录和经审核的材料。来源不同，时间与范围也不同。
- **B2 · 处理。**收集脚本把相关材料整理为数据快照；程序界面与经过检查的材料共同参与构建。快照是保存某次数据状态的文件，不等于实时数据。
- **B3 · 呈现。**构建后的网页让使用者浏览观测、对象关系与研究材料；部分个人整理与导出发生在浏览器中。
- **B4 · 解释。**文档导航分别提供当前状态、数据范围、架构、历史与决定等入口；它们帮助读者了解数据和功能的含义。

这里的**脚本**是完成一组操作的程序；**构建**是把源文件及相关材料处理成可发布或运行成果的过程。理解材料 B 时，重点是看到“来源—处理—呈现”之间需要说明和检查，而不是记住所用编程语言。

| 材料类别 | 主要用途 | 阅读时提出的问题 |
| --- | --- | --- |
| README 与使用文档 | 向人介绍目的和开始方式。 | 我能用它完成什么，前提是什么？ |
| 源代码与脚本 | 表达界面、计算或处理过程。 | 哪部分负责取得、处理或展示材料？ |
| 数据及其说明 | 保存记录并解释来源、范围和时间。 | 一条记录表示什么，覆盖到哪里？ |
| 配置与依赖说明 | 告诉程序怎样运行、需要哪些组件。 | 运行要求是什么，与我的条件相符吗？ |
| 测试与检查记录 | 检验预先规定的行为或规则。 | 实际检查了什么，哪些效果还没验证？ |
| 状态、贡献与权利说明 | 说明项目阶段、参与方法和复用条件。 | 什么尚未完成，我可以怎样参与或使用？ |

这张表也适用于阅读自己的研究项目：报告相当于对人的说明，数据表保存依据，生成页面的程序负责呈现，检查记录说明你验证了什么。文件名称可以不同，承担的职责应当清楚。

### 2.2.3 来源、版本与判断范围

阅读完整项目以后，学习者会积累多种信息。为了让别人理解自己的结论，应当区分三种表达。

| 表达层次 | 项目阅读中的例子 | 所需依据 |
| --- | --- | --- |
| 来源记载 | “该版本 README 说明研究执行尚未接通。” | 对应文档及具体位置。 |
| 个人观察 | “我打开示例并成功导出一份报告。” | 实际完成的操作、条件与结果。 |
| 分析判断 | “这个示例可能适合练习检查引用。” | 从材料到用途的理由；效果仍待检验。 |

没有实际操作时，只能把第二项改为“文档介绍了导出方式”。引用教材提供的卡片也可以完成分析，但应写明是教材材料阅读。诚实区分学习路径，能够使同伴提供更准确的帮助。

**版本**是成果在某一阶段的状态。仓库中的一次**提交（commit）**记录一组变化，并有可定位的标识。指向固定提交的链接，可以把读者带回当时的文件；指向 `main` 等分支的链接通常随新提交移动，适合查看当前情况。

阅读档案至少需要记录来源名称、链接、材料位置和实际查阅日期。如果结论依赖当时的规则或状态，还应记录固定提交或发布版本。本章材料链接保留固定提交，便于复查；具体项目当前状态应另看最新说明。

日期也可能有多种含义：数据观察日说明记录对应的时间，文档更新时间说明文字何时变化，查阅日期说明自己何时取得材料。第一章模型网络的数据观察日与截图日期不同，正是一个例子。把它们混成“最新数据”，会使读者误判材料覆盖的时间。

可追溯帮助别人复查，结论仍需与材料范围相称。README 说明发布者怎样介绍功能，不能单独证明课堂使用效果；测试记录说明检查过的行为，不代表所有场景可靠。可以把缺少依据的结论缩小，或者转化为下一步问题。

材料的公开状态也需要如实描述。OpenDipper 在本章固定快照中的根目录应用许可尚未选定，代码、数据、地图和品牌的条件需要分别确认[3]。我们可以阅读其公开建设过程，但不能由此推断全部材料已统一授权。第三章再具体讨论复用；这里保留实际状态与出处即可。

## 2.3 不同项目的材料与复用入口

### 2.3.1 软件与工具项目：功能和使用条件

软件工具需要解释它帮助完成什么操作、如何运行，以及遇到问题怎样获得支持。准备使用工具的人需要运行说明，准备理解设计的人可能优先阅读架构和开发文档。取得软件不等于完成了具体任务，实际表现要结合使用条件检验。

**材料 D：DSH 的软件、文档与参与入口。**以下分别依据同一固定版本的中文 README 与贡献指南整理[8][10]，供本章独立制作画像。

- **D1 · 对象。**DeepSeek Harness（DSH）是 DeepSeek AI 开发的开源智能体框架，README 介绍了以插件组织功能的设计。
- **D2 · 成果与材料。**仓库提供程序源码与启动 Web 界面的说明，并链接使用指南、开发指南和架构文档；本章只阅读这些入口，不要求安装。
- **D3 · 使用范围。**该版本标注为开发者预览，提示可能发生不兼容的变化；README 提供 MIT 许可与第三方依赖说明入口。阅读说明不等于已经验证某项任务效果。
- **D4 · 参与路径。**贡献指南在该快照中暂不接收外部 PR，但欢迎通过 Discussions 反馈问题，以及分享插件、撰写指南和帮助他人；实际参与前需重读当前规则。

材料 D 足以回答项目画像中的基本问题：它是什么、提供什么、从哪里读、怎样参与。需要进一步判断“是否适合我的任务”时，还应结合运行条件和具体测试。Discussions 是问答与交流的讨论空间，项目如何使用它由参与规则说明。

### 2.3.2 AI 模型项目：模型说明与开放材料

**模型卡（Model Card）**是模型仓库中介绍模型的说明，通常包含用途、使用方法、限制、训练或评价信息；Hugging Face 的模型卡通常由 README 文件承载，并可包含结构化元数据[6]。卡片提供查证入口，不自动保证每个栏目齐全或每个结论经过独立验证。

R1 的模型文件目录除 README 外，还可以看到配置文件与分片保存的权重文件[7]。配置帮助程序正确加载，权重保存模型计算所需的数值。对研究模型来源的人，技术报告更重要；对准备运行的人，模型文件、配置和运行要求更重要。只为理解项目，无需先下载这些大文件。

同一项目可能发布多个模型条目。名称相近不代表对象相同，版本、基础材料与使用条件需要分别核对。本章重点是知道去哪里查找信息，模型训练和派生方法将在后续学习中展开。

**材料 E：R1 模型项目的阅读入口。**以下依据固定 README 和模型文件目录整理[7]。

- **E1 · 对象。**DeepSeek-R1 是 DeepSeek-AI 发布的模型项目，README 将其作为推理模型介绍。
- **E2 · 成果。**说明中列出模型下载与研究报告入口；模型文件目录提供配置和权重等运行材料。
- **E3 · 阅读选择。**了解方法先看报告，了解怎样运行先看使用说明及条件；不同模型条目的名称与材料需要分别核对。
- **E4 · 尚待查明。**这组材料不提供完整社区贡献规则，也未证明模型适合自己的任务；画像中可以明确标出待查项，不能替项目补写承诺。

模型卡与说明帮助人找到证据，不能只看栏目是否齐全就判断质量。对许可、训练材料或评测的具体主张，应继续阅读相应来源。

### 2.3.3 数据与研究项目：口径、方法和成果

数据项目需要解释记录了什么、如何取得和处理、覆盖到哪里。研究项目还需要说明材料怎样支持结论。同样一张表，可能记录一次快照，也可能汇总一段时间的活动；理解口径，才能知道哪些比较有意义。

OpenDipper 与 OpenDigger 是不同项目。根据材料 B，可以进一步表述：OD 把 OpenDigger 等来源提供的材料用于观测与研究功能；这是一种具体的数据来源关系，不能因此说二者是同一个项目。

项目中的“关系”还可能表示软件运行时需要另一个组件，或两个项目拥有共同参与者。前者属于**依赖**，后者反映人的参与联系。OD 的开源星系说明区分记录关系与推断关系；记录的共同贡献者关系并不等于软件依赖，也不等于质量排名[1][4]。

**例 2-2　图上相邻，就能认定有技术依赖吗？**不能。应先查看连线类别及来源。如果连线表达共同贡献者，只能在相应记录范围内讨论参与联系；若要确认技术依赖，应继续查找依赖声明或相关程序说明。没有追到合适材料之前，图形只是调查入口。

比较项目时，应以任务为依据。研究语言模型的方法，可以读 R1 技术报告；研究生态关系的表达，可以读 OD 的数据和关系说明；研究智能体如何组织功能，可以读 DSH 的文档。三者服务不同需要，不能直接用同一条排名代替选择。

本教材本身也可以作为内容项目观察：它交付正文、图件、练习和网页，质量需要从概念、依据、阅读体验与反馈理解。没有模型权重不妨碍内容项目参与开放协作。共同阅读框架需要与具体成果结合。

## 2.4 项目背后的社区与协作

### 2.4.1 使用者、贡献者与维护者

项目公开以后，使用者会发现作者未曾预料的情境：某个术语难懂，某条来源过时，某种操作容易出错。将这些困难转化为可讨论的材料，是社区改进项目的一个起点。

**贡献者**提供代码、文档、数据、反馈或其他有用改进；**维护者**持续负责方向、评审、整合和发布等工作。这些角色不是固定身份，一个人可以同时使用、贡献与维护不同项目。参与价值也不能简单用提交数量衡量：一条准确的来源纠正，有时比大量无依据的内容更有帮助。

**材料 C：OpenDipper 的参与入口。**以下依据 CONTRIBUTING 与公开 Issue #19 整理[2]。

- **C1 · 谁可以参与。**使用者、领域研究者和开发者可以参与，也可以借助 AI 工具；人提出需要、提供领域知识并评审成果。
- **C2 · 怎样开始。**先查看现有任务与贡献说明；需求反馈可以说明谁遇到什么问题、希望得到什么结果，不必先制定代码修改方案。
- **C3 · 一个真实任务。**Issue #19 邀请参与者围绕一个 AI 与开源主题，整理 3—5 个原始来源，附日期及简短的价值说明。
- **C4 · 怎样处理。**材料与实现需要按项目过程接受审核；提交反馈不会自动启动 AI 执行，也不意味着建议已被采用。该 Issue 在本章查阅时仍是开放的任务邀请。

C3 与本课研究实践有直接联系：识别主题、找到原始材料、解释为何有用，本身就可能服务于社区。这里列出的是社区真实提出的需要，不是教材虚构的“学生已经成功贡献”故事。学习者可以先在自己的作业中练习这种材料整理，再根据能力、意愿和项目当前规则决定是否参与。

### 2.4.2 问题讨论与修改建议

**Issue** 是记录和讨论问题、建议或任务的入口。一个好的问题报告会交代发生情境、实际结果、预期结果以及可检查的依据。它让维护者理解需要，但不一定包含解决方案。

**Pull Request（PR，合并请求）**则把一组具体文件变更提交给项目评审，便于查看改了什么、讨论差异、运行检查并决定是否合并。它不只用于代码，也可以用于文档。Issue 与 PR 可以相互关联，但二者并非必须成对出现：一个 Issue 可能经解释而解决，一个小文档修订也可能按规则直接提交 PR。

![Issue 与 PR：两种独立的协作入口](../assets/figures/ag-02-02-issue-pr-workflow.webp)

图 AG-02-02 复用原版 AIOS101 的协作插图[9]。两条入口都需要人的判断与后续处理：提出问题不等于已经修好，提出变更也不保证合并。图中的人物和工作台是概念表达，不是某次社区活动的照片。

本章先读懂协作过程，不要求操作分支、提交 PR 或向上游发帖。后续章节以 AtomGit 示范发布与共同修订，学生可以使用给定作品或自己的成果。

### 2.4.3 贡献指南与参与方式

DSH 的一份固定版本贡献指南说明：当时处于早期积极开发阶段，暂时无法接收外部 PR；同时欢迎通过 Discussions 报告问题，创建插件，撰写文章与操作指南，以及回答其他成员的问题[8]。**Discussions** 是面向问答和交流的讨论空间，与项目用来跟踪任务的 Issue 有不同侧重，具体用途仍由项目约定。

这个对照说明，开放协作不是“所有人随时向所有项目提交任何修改”。维护者需要根据阶段与能力安排入口，参与者则应阅读当前指南。OD 欢迎的一种提交形式，不能自动成为 DSH 的规则；某个固定版本的规则，也不能永远代表项目未来的安排。

如果使用 AI 协助整理来源或起草反馈，参与者仍须核对内容，说明实际做过的工作，并承担自己提交内容的责任。AI 可以帮助协作，贡献是否有用要由实际问题、证据和评审共同判断。

## 2.5 综合实践：制作一份项目画像

### 2.5.1 任务与完成要求

**项目画像**是围绕明确问题，依据材料形成的结构化介绍。本章画像说明项目的目的、成果、材料与协作，不进行无依据的评分或排名。它可以是一至两页文字与表格，也可以采用清楚的图文形式。

选择一个对象即可：使用材料 D 研究 DSH，使用材料 A—C 研究 OpenDipper，或使用材料 E 及相应说明研究 R1。也可以选择材料条件相当的其他项目。各路径都从本章材料开始，无需第一章简报或实际运行项目。

1. 写明项目身份、读者需要、主要成果及当前范围。
2. 选择至少两类承担不同作用的材料，解释各自回答什么问题，留下来源与位置。
3. 依据现有材料说明参与入口和规则；尚未查到的内容标为待查，不补写。
4. 区分来源记载与自己的分析，提出一个仍需调查的问题。

AI 可以协助翻译、整理和图文表达，材料是否相关及结论是否成立仍需自己判断。你应能解释一项材料选择。完成核心任务后，可选另一类型项目作短对照，也可在自己的画像中补充一次修订。

### 2.5.3 自我评价与后续学习

自查时，看看读者能否回答四个问题：项目为什么存在，提供什么成果，材料怎样支持理解，可以怎样参与改进。再检查你的每项关键说法能否回到材料，尚未确定的部分是否明确。

本章承接第一章的概念与材料判断方法，实践成果独立完成。第三章《开源协作与创新》将解释复用和共同改进的机制，并提供新的材料与待改说明。你可以选择继续自己的画像，也可以使用下一章的独立输入开展练习。

## 本章小结

理解项目需要联系目的、成果、材料与协作。仓库组织文件和历史，平台承载多个项目，二者都不能替代项目全貌。按问题阅读 README，再选择相关材料，有助于形成清楚的阅读路线。

软件工具、模型、数据与内容项目有不同的成果和材料要求。版本、日期、来源与实际观察范围帮助读者复查；公开可见与许可复用分别说明。Issue、PR 和讨论空间提供协作入口，具体规则取决于项目及其阶段。

一份有用的项目画像说明已知、依据和待查问题。它可以独立形成，也可以在后续继续扩展。能够解释自己的材料选择，比机械填满所有栏目更重要。

**关键概念：**项目、仓库、平台、README、数据快照、模型卡、贡献者、维护者、Issue、PR、版本与项目画像。

## 思考与练习

### 基础理解

1. “打开代码仓库，就取得了一个项目的全部材料。”这句话忽略了什么？可用本章任一项目举例。
2. 选择一个项目，用目的、成果、材料与协作四个问题组织一段介绍。四者为什么需要联系起来？
3. README、模型卡和贡献指南各适合回答什么问题？为什么不是每个项目都需要模型卡？

### 材料分析

4. 根据材料 D，判断：“提供了启动说明，所以我已经验证它适合我的任务”；“该快照处于开发者预览，因此实际使用前应查当前条件”。分别说明依据。选做：用材料 A、B 分析为什么展示报告不等于已运行研究服务。
5. 根据材料 C、D，评价“不会编程就无法贡献”“开放项目必须接收所有外部 PR”两句话。参与前为什么需要读当前指南？

### 拓展与迁移

6. 为一份开源学习指南设计项目画像：说明读者、成果、两类必要材料和反馈入口。它与模型项目需要的材料有哪些不同？不要求实际建仓库。

### 参考解答与学习提示

**第 1 题。**项目可能跨多个仓库和站点。模型项目还可能有模型文件与研究报告入口，数据研究项目可能引用上游数据。应按问题继续追查。

**第 2 题。**如研究 DSH 的学习入口：目的关系到组织智能体工作，成果包括软件与文档，材料包含 README 和指南，协作可从有依据的问题反馈开始。四者相互解释，不能只列平台名称。

**第 3 题。**README 帮助了解项目与起点，模型卡说明具体模型，贡献指南说明参与规则。材料要求取决于成果，纯文档项目不需要模型权重或模型卡。

**第 4 题。**第一句把文档说明当作个人运行结果；还需任务、条件与实际检查。第二句符合 D3，并承认快照不能永远代表现状。选做中，A4 明确区分编写示例与研究执行，B 说明材料处理与呈现过程。

**第 5 题。**两句都不成立。材料列出非代码参与，贡献指南也可能限定接收方式。当前规则决定实际参与的路径，历史快照用于理解，不替代提交前核对。

**第 6 题。**指南可以帮助初学者找到概念与例子，材料需要可靠来源和使用说明，反馈入口可以用于报告不清楚的术语。模型项目则还需模型及评测等材料。评价重点是材料是否服务成果、反馈能否帮助改进。

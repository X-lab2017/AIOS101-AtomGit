# 找到值得解决的问题：从观察到设计

> 状态：review
> 版本：0.2.0

你已经能读项目材料，能解释模型学习、文字生成和工具行动，还留下了一份逐步完善的 DSH 导览。现在，观察站要迈出新的一步：把自己的理解，变成别人用得上的东西。

想象一位同学读完导览说：“我知道它能帮忙整理材料，可我还是分不清，是模型把文件保存了，还是 DSH 保存了？AtomGit 又在哪一步？”这是一个可以继续探索的起点。相比“我要做一个功能丰富的 AI 网站”，它更具体，也更容易看出作品有没有帮上忙。

本章先不急着制作。我们会把这个问题写成一份简短的设计说明。它不是交给老师看的长报告，而是你在下一章与 AI 一起创作时，用来决定做什么、删什么、何时可以停下的依据。没有接入 DSH，也能完成本章。

## 7.1 从“我想做什么”转向“谁遇到了什么”

**用户**是实际使用作品的人。阅读指南的同学、观看图解的老师，都是用户。**需求**是他们在某种情境下想完成的事情；网站、视频、插件则是可能采用的解决办法。把两者分开，能给创作留下选择余地。

“同学需要一个聊天机器人”已经选定了形式。再问一句“他想借它完成什么”，可能得到完全不同的答案：他想辨认模型和工具的分工，也可能想找到安装入口，或比较两次生成结果。这三个问题未必需要同一种作品。

![纸面上铺满不同创作工具，一只取景框只圈住一个需要解释的局部，其他想法暂留在框外](../assets/figures/ag-07-01-focus.webp)

取景框没有宣告框外的事不重要，只是让这一版作品有明确的焦点。选题也一样：先为一个具体情境解决一个问题，作品才有机会从想法变成可用的成果。

本篇用一个**作者设计的教学情境**贯穿三章：一位没有编程基础的同学读了 DSH 导览，想解释“一次整理材料的任务是怎样完成的”，却把生成文字、写入文件和公开分享混在一起。这个情境用于练习设计，不是已经完成的访谈结论。它对应的作品暂定为“从材料到导览”的角色地图，一页文字也可以做成这张地图。

如果你自己在前六章遇到过类似困惑，可以从亲历的问题开始；如果没有，就把它当作**待验证的假设**——当前认为可能成立、还要通过观察检查的想法。不要为了让选题显得重要，编出“很多同学都这样说”。

### 把问题写到可以讨论的程度

比较下面两种写法：

| 写法 | 为什么难以或容易推进 |
| --- | --- |
| 帮助所有人理解 AI | 谁、哪种理解、遇到什么困难都不清楚，几乎任何内容都能装进去 |
| 帮助读过 DSH 简介的初学者，沿“材料变成导览”的例子，分清生成文字、写入文件和分享成果的职责 | 读者起点、具体任务和困惑都出现了，可以据此挑选内容 |

你也可以先写一句：“当____想要____时，会卡在____；我想帮助他/她____。”空格是思考的支架，不是必须照抄的格式。问题写得越具体，下一步越容易判断某个功能究竟有没有用。

## 7.2 看看作品出现之前，别人是怎样做的

读者不会在空白世界里等待我们的作品。他可能直接看 README、向同学问一句、翻课程章节，或者把问题交给聊天工具。**现有办法**是作品出现前已经可用的解决方式，纸笔和口头解释也算。

先沿其中一种办法亲自走一遍。以角色地图为例，打开自己的导览，找找“模型”“工具”“工作区”出现在哪里。导览可能已经讲清 DSH 是什么，也给出任务例子，但几个职责分散在不同段落。新作品的价值便可能是把它们放到同一个具体任务里，减少读者来回拼接的负担。若现有导览已经清楚，直接补一句解释也许就够了，不必为了“做项目”再建一个网站。

有同伴时，可以请他回想一次具体经历：“你上次想弄懂这件事时，先看了哪里？在哪一步停下？”先听他怎样描述，再决定改什么。问“你是不是需要一张漂亮图？”会把答案引向自己喜欢的形式。GOV.UK 的用户研究指南也强调从人的任务和现有做法出发，并把缺乏证据的意见作为假设处理。

自学者可以重走自己当时的阅读过程，记下一处实际不顺畅的位置；这能提供设计线索，但不能证明其他人都会遇到相同问题。此处只需留下一个有用观察，不要求提交访谈表或收集个人信息。

### 选择一个值得先做的问题

如果观察站里有多个问题，不必给它们做复杂评分。对每个候选问三句：**解决后能帮助谁？我手里有什么材料？这一版能否做得足够小？**

例如，“比较所有模型的优劣”需要大量材料，也很难为所有用途得出同一个结论；“把自己已经做过的生成对照解释清楚”更容易落地。“给 DSH 做全部功能导航”可能过大；“说明一次文件任务中的角色”则已有第六章的机制知识和导览作基础。

小并不等于浅。一张把关系讲对、让人会判断的图解，可能比罗列二十个术语的长文更有价值。若实际观察表明同学早已分清这些职责，就换一个确实存在的问题，不必为了沿用示范而继续证明它。

## 7.3 先选表达方式，再守住范围

**作品形式**是内容到达读者的方式。怎样选，取决于读者要做的事：需要逐步操作，可以写任务指南；需要比较差异，可以做对照说明；需要理解关系，可以做图解；需要反复处理同类材料，才可能值得做小工具。

角色地图选用“一页文字配关系图”，理由是读者需要把几个职责放在一起理解。第一版可以只用标题、短段和简单表格，不需要网站账户、动画或额外安装。若读者主要通过听觉学习，也可以改成带文字稿的短音频；若你的问题本来是操作困难，就应换成任务指南，而不是强套这张地图。

**范围**规定这一版覆盖到哪里。它同时包含“做到什么”和“留到以后”。为角色地图，我们保留：一个材料整理任务、必要角色的通俗解释、文件保存与分享的区别，以及一道让读者试着判断的新情境。安装教程、所有插件、不同模型排名先不进入这一版。

假如 AI 建议再加入术语百科、自动测验和作品排行榜，先回到问题：“少了这一项，读者还能分清本次任务的职责吗？”能，就可以暂缓。把功能删掉并不是浪费创意，而是让最需要解释的关系更醒目。

还要考虑自己的材料和时间。拿不准的功能不先写成承诺；没学过编程也无须为了作品外观临时学会整个开发流程。先选自己能打开、能修改、能解释的形式，之后再扩展。

## 7.4 把“完成”写成能够检查的变化

“内容丰富、界面美观、体验友好”可以表达愿望，却难以判断这一版是否完成。**完成标准**是你愿意用具体行动检查的条件。它把设计和后面的检验接起来。

对角色地图，我们先约定三个标准：

1. **内容说得对：**生成文字、文件读写、工作区和人的决定能分清；DSH 的职责有固定版本材料依据。
2. **作品能使用：**离开作者口头讲解，读者仍能找到例子的输入、结果和阅读顺序；手机上能阅读主要文字，不能只靠颜色区分角色。
3. **理解有迁移：**面对“聊天里已有导览，但指定文件不存在”的新情境，读者能说明还缺文件写入或保存及检查，不能直接判定任务已经完成。

![读者的困惑对应作品中的讲解，再对应可以观察的理解检查；装饰功能没有直接替代这条对应关系](../assets/figures/ag-07-02-need-to-check.svg)

第三条中的**迁移**，是把刚理解的方法用到稍有不同的情况。照抄图上的定义未必说明理解了，判断新情况更能暴露关系是否讲清。第九章将具体实施这些检查。本章只需定下标准，不把“打算检查”填成“已经通过”。

标准也可能需要调整。例如第一次草稿太长，无法一屏显示，这未必是失败：一屏不是本例的必要目标，读得清楚才是。若你最初约定“一分钟内读完”，却没有依据支持这个时长，可以改为“能独立找到任务结果”，并说明调整原因。不要在检验失败后悄悄降低标准，只为宣布成功。

### 一份完整而简短的设计说明

下面是作者示例，用来展示各项之间怎样互相支持；没有包含实际用户反馈。

| 设计问题 | 本例的决定 |
| --- | --- |
| 给谁、在何时使用 | 读过 DSH 简介、准备理解一次材料整理任务的初学者 |
| 想解决什么 | 把生成、写文件和分享混为一件事，不知道结果应该出现在哪里 |
| 目前怎样解决 | 回看导览和第六章，自己拼接角色关系；这是本例需要验证的设计假设 |
| 手中材料 | 已有导览、第六章任务或机制笔记、固定版本 DSH 架构与使用指南 |
| 做成什么、覆盖哪里 | 一页角色地图，讲清一个任务；保留必要来源和自测，不加入安装或排行榜 |
| 怎样检查 | 对照来源核对职责；实际打开检查阅读；用“有回答却无文件”的情境检查理解 |

这里没有完整答案式的成品。你仍要决定先讲什么、哪个例子最贴切、删去哪段，以及怎样让读者自然看见关键关系。下一章就从这些决定开始。

## 7.5 为你的观察站写一份设计说明

打开[第七章材料包](../../practice/ch07/README.md)，把 `ch07` 文件夹放进观察站。回看自己最近的导览或问题记录，在 `work/design.md` 中写下：读者与情境、一个问题、现有办法、准备使用的材料、作品范围和三个完成标准。它们可以连成几段短文，不必把模板写满。没有自己的问题记录时，先用上述作者情境练习；没有前章导览时，第八章材料包提供参考稿，可继续制作，但来源阅读和实际任务目标仍按前章要求补足。

选用角色地图示范时，保留其“设计假设”标签；选择自己亲历的问题时，写清观察发生在哪里。材料只需列路径或链接，不必再复制前六章所有文件。若发现只需改导览中的一个小段落，也可以把那次改进作为作品范围。

写完后，试着删去最想加的一项功能。如果核心问题仍然得到解决，就把它放到“以后再考虑”。再检查三个标准是否分别落到了内容、使用、理解或效果上，避免全都只是“写了几百字、画了几张图”。本章交付这一份设计说明即可，不要求制作成品。

### 停下来想一想

1. “我要做一个 DSH 网站”为什么还不是清楚的需求？
2. 角色地图如果已经解释清楚职责，是否必须再做交互动画？
3. 没有访谈过读者，如何诚实地开始设计？
4. 把“图解很专业”改成一个可以检查的标准，你会怎样写？

**参考反馈：**第一题还缺使用者、情境与要解决的问题。第二题取决于动画是否帮助当前任务，不是功能越多越完整。第三题可从自己的经历或明确标记的假设开始，随后验证。第四题可以是“给出一个未在例子中出现的文件任务，读者能区分文字生成与文件保存”；画得像专业图表并不能单独证明理解。

你现在有了一个可以动手的约定：为谁解决什么问题，凭什么材料，做到什么程度。下一章，我们让它长出第一版可以阅读的样子。
